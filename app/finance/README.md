# Учёт KORT - пакет `app.finance`

Управленческий учёт компании: счета и остатки, журнал операций, отчёты,
платёжный календарь, выписки банков, реестр договоров, люди и права.


## Из чего состоит

| Файл | Ответственность |
| --- | --- |
| `db.py` | схема `finance`, сессии, `create_all` для тестов на SQLite |
| `models.py` | что считается правдой, а что производным; три ключевых решения объяснены в докстринге |
| `service.py` | справочники, операции с версионной правкой, применение импорта |
| `importing.py` | чтение файлов: колонки по названиям, шапка в две строки, реквизиты выписки над и под таблицей, порядок дат на файл, переводы между своими счетами, построчные замечания |
| `formats.py` | формат по содержимому, а не по расширению: xlsx, старый .xls, HTML- и XML-таблицы под видом .xls, выгрузка банк-клиента 1С, CSV |
| `banks.py` | номер счёта (IBAN), БИН в ячейке контрагента, банк по БИК и коду в IBAN, подсказка имени нового счёта |
| `reports.py` | деньги, прибыль, долги, проекты, календарь, план/факт, контрольные суммы |
| `grid.py` | журнал как лист Univer; правка ячейки = правка операции; ответ правки - готовая строка листа (`row_of`) |
| `export.py` | журнал в `.xlsx` с теми же фильтрами: даты и числа, приход/расход/перевод, итоги по видимым строкам |
| `autotag.py` | авторазметка статей по тексту операции: целые слова, тип операции банка первым, деловые статьи раньше бытовых; одна запись в истории на разметку |
| `statements.py` | PDF-выписка → строки импорта плюс остатки, напечатанные банком (сверка при загрузке) |
| `auth.py` | вход по почте и по номеру, сеансы, ограничитель перебора, `resolve()` со снимком прав |
| `access.py` | разделы прав, «личное поверх отдельского», права на запрос одним запросом к базе |
| `people.py` | отделы, сотрудники, учётки по номеру, сброс, блокировка, сеансы; кто кого меняет |
| `history.py` / `audit.py` | журнал действий: запись с автором, сеансом и адресом из контекста запроса; лента с фильтрами, просмотры, очистка |
| `notifications.py` | «Ждут решения»: просьбы о сбросе, пять неверных паролей, «пароль задан» |
| `cli.py` | команды сервера: сброс пароля владельца |
| `trash.py` | корзина: всё удалённое (договоры, операции, юрлица, поля, значения, листы, отделы, сотрудники, справочники) - восстановить или удалить насовсем; используемое насовсем не стирается |
| `contracts/summary.py` | «Оплачено (сводка)»: книга-сводка компании в Google, колонки по названиям, договор по номеру и клиенту без угадывания |
| `onec/` | базы 1С компании (раздел «Интеграции → 1С»): `client.py` - адрес базы и запросы к её REST-сервису, `sync.py` - чтение документов в `onec_documents`, `match.py` - документ к договору реестра, `service.py` - базы, месяц по договорам, решения человека. Подробнее - «1С» ниже |
| `secretbox.py` | пароли подключений к чужим системам (REST-сервис 1С) лежат в базе зашифрованными ключом `FINANCE_SECRETS_KEY` |
| `models.SheetLook` + `../api/routes/finance_looks.py` | личный вид листов (ширины, цвета, перенос) - у каждой учётки свой; собирает фронт (`src/components/univer/look.ts`) |
| `layout.py` | привязка колонок к листу по названиям, а не по номерам |
| `../api/routes/finance*.py` | HTTP-маршруты и права - **единственное место**, где пакет встречается с HTTP |

## Права

* Роли - `owner`, `admin`, `employee`. Владелец и администратор видят всё;
  сотрудник - то, что записано ему лично или его отделу (`access.py`).
* Каждый маршрут `/finance/*` объявляет раздел: `require_access(раздел,
  "view" | "edit")`. Обход маршрутов в `tests/test_finance_access.py` падает
  на необъявленном, `tests/test_finance_audit.py` - на изменяющем маршруте
  без события в журнале.
* Учётка, ждущая пароль или заблокированная, не открывает ни одного
  маршрута; временный пароль открывает только его смену.
* Пароль владельца через API не сбрасывается никем. Команда сервера:

  ```
  python -m app.finance.cli reset-password owner@company.kz          # временный пароль, смена при входе
  python -m app.finance.cli reset-password +77011234567 --password …  # задать пароль
  ```

## Настройки (префикс `FINANCE_`)

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `FINANCE_ENABLED` | `true` | `false` - раздел отвечает 404 |
| `FINANCE_BASE_CURRENCY` | `KZT` | валюта компании при создании пространства |
| `FINANCE_IMPORT_MAX_ROWS` | `20000` | потолок строк в одной загрузке |
| `FINANCE_IMPORT_MAX_MB` | `15` | потолок размера файла |
| `FINANCE_GRID_MAX_ROWS` | `10000` | сколько операций отдаётся в табличный вид |
| `FINANCE_SECRETS_KEY` | пусто | ключ шифрования паролей подключений; пусто - базу 1С не подключить. Сменили ключ - пароли баз вписываются заново |
| `FINANCE_ONEC_SYNC_MINUTES` | `30` | как часто сервер сам перечитывает базы 1С; `0` - только кнопкой «Обновить» |

## Почему устроено именно так

Короткий ответ - в `docs/finmap-audit.md`: там протокол проверки чужого
импортёра двадцатью файлами и список того, что он делает с человеческой
неточностью. Каждое решение этого модуля - ответ на конкретную строку оттуда.

Три главных:

1. **Файл не отвергается целиком.** Хорошие строки заводятся, плохие остаются
   в партии импорта с объяснением и правятся по одной.
2. **Не угадываем там, где ошибка тихая.** Порядок частей даты решается один
   раз на файл по всем датам; нет ответа в данных - раздел спрашивает. Знак
   суммы задаёт вид операции, а не теряется.
3. **Отчёт доказывает свою правоту.** Контрольные суммы показываются всегда, а
   не пишутся в лог: разбивка сходится с итогом, переводы свёрнуты в ноль,
   разнесение по проектам не превышает суммы операции. Выписка любого формата
   (PDF, Excel, 1С) при загрузке сверяется с остатками, которые напечатал банк.

Пределы значений держат `service.check_money` и `check_date`: сумма меньше
10^12 и округлена до копеек одним правилом везде, дата - в 2000–2100. Всё, что
пишет деньги (операции, счета, счета-фактуры, планы), проходит через них -
иначе Postgres отвечает пятисотой, а округление расходится между экранами.

## 1С

Каждое юрлицо группы ведёт свою базу 1С («Бухгалтерия для Казахстана»,
обычно в 1С:Fresh). KORT только читает её через автоматический REST-сервис
(OData): в базе «Администрирование → Синхронизация данных → Настройка
автоматического REST-сервиса» - отдельный пользователь с паролем и на вкладке
«Состав» отмечены:

* справочники `Организации`, `Контрагенты`, `ДоговорыКонтрагентов`;
* документы `СчетНаОплатуПокупателю`, `РеализацияТоваровУслуг`,
  `СчетФактураВыданный`, `ПлатежноеПоручениеВходящее`;
* по желанию - документ `ЭСФ` и регистр сведений
  `СведенияПоАктамВыполненныхРабот` (дата подписания акта). Без них база
  читается, а под базой остаётся замечание, чего не хватает.

Что из этого следует:

* **Документ к договору - по номеру и клиенту, без угадывания** (`match.py`).
  Номер договора из 1С сравнивается с номером в реестре (сначала точно, потом
  без разделителей), клиент - по названию без формы собственности, по
  латинице-двойнику (ATEX и АТЕХ) или по БИН. Два подходящих договора - документ
  остаётся «без договора» с кандидатами, а не ложится на первый.
* **Решение человека важнее сопоставления.** «К договору» и «не по договору»
  хранятся у документа и не перетираются следующим чтением; привязка к договору
  запоминает название клиента из 1С как второе имя клиента (`source = "1c"`).
* **Месяц - месяц услуги, как в книгах BBC.** Счёт 29.09 «за октябрь» стоит в
  октябре: месяц берётся из периода услуги, у АВР - из отчётного периода,
  счёт-фактура и ЭСФ идут за своим АВР, оплата - за своим счётом.
* **Удалённое и пропавшее не стирается.** Документ с пометкой удаления
  остаётся с пометкой, пропавший из окна чтения - с отметкой `gone`; решения на
  них сохраняются.
* 1С:Fresh прячет ошибки 1С за переадресацией на «приложение недоступно», а
  неверный пароль и неверный номер базы дают один и тот же пустой 401. Поэтому
  отказ под базой говорит, что проверить, а не цитирует сервер.
