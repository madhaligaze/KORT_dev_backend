# Актуализация реестра KORT из Google Таблиц - инструкция для скрипта или ИИ-ассистента

Для того, кто вносит данные в KORT снаружи - например, Claude коллеги со
своим доступом к книгам Google и **без** исходного кода KORT. Исходники не
нужны: KORT - веб-приложение с HTTP API, и всё ниже делается обычными
запросами от имени своей учётки, как это делал бы человек в браузере.

Щёлкать таблицу KORT через Playwright не нужно и не стоит: лист - это холст
(canvas), кириллица туда при автоматическом наборе не попадает, адреса
ячеек сдвигаются. Для скриптов есть шлюз сверки - он ниже.

## 1. Вход

Базовый адрес API: `https://kort.cards/api/backend/api/v1/finance`

Нужна учётка KORT с правом «Договоры - правит». Логин и пароль даёт
владелец реестра.

```
POST /auth/login          {"email": "…", "password": "…"}         - вход по почте
POST /auth/phone/login    {"phone": "+77011234567", "password": "…"} - вход по номеру
POST /auth/logout                                                    - выйти в конце
```

Сеанс - в cookie ответа; держите одну HTTP-сессию на весь прогон
(`httpx.Client`, `requests.Session`) и в конце вызовите `/auth/logout` -
он закрывает только этот сеанс, остальные входы той же учётки не трогает.

### Если учётка общая (например, владельца)

Под одной учёткой могут работать несколько человек одновременно - сеансы
независимы. Чтобы никому не помешать:

- **Пароль вводить точно.** Пять неверных паролей подряд закрывают вход по
  этой почте на время - для всех, кто ею входит. Получили 401 - не
  повторять вслепую, спросить владельца.
- **Не вызывать ничего, кроме** `/auth/login`, `/contracts/schema`,
  `GET /contracts`, `POST /contracts/sync`, `/auth/logout`. У владельца
  открыто всё - смена пароля и почты выкинет или не пустит остальных,
  «Передать владение» и «Настроить реестр» меняют компанию целиком.
- **Не закрывать чужие сеансы** (`/auth/sessions…`).
- **Подписывать сверку** в поле `source` - откуда и кто: «Google: Разовые ·
  Claude <имя коллеги>». Правки договоров в истории будут подписаны
  учёткой, а подпись сверки в журнале действий покажет, чья это работа.

## 2. Какие поля есть в реестре

```
GET /contracts/schema
```

`fields[]` - ключ (`key`), подпись (`title`), тип (`type`). `lists` -
допустимые значения списков по ключу поля (`status`, `type`, `subject`…).
Значение закрытого списка пишется точно так, как в `lists` (например,
статус «На исполнении», а не «в работе»).

Поля реестра BBC (на 29.09.2026):

| Подпись в KORT | Ключ | Что писать |
| --- | --- | --- |
| Текущее состояние | `status` | одно из: Действующий, На исполнении, Приостановлен, Исполнен, Недействующий, Не состоялся |
| Папка договора | `folder_url` | ссылка (в книгах - «Ссылка на Битрикс 24») |
| Планируемый срок завершения | `planned_end_at` | дата `дд.мм.гггг` («до 15.07.2026» тоже читается) |
| Ответственное лицо | `people` | имя сотрудника как в KORT; несколько - через запятую |
| Исполнитель | `executor` | только наше юрлицо: BBC, BBCA, BBC legal support, … |
| Заказчик | `customer` | название клиента |
| № Договора | `number` | как в книге |
| Дата заключения Договора | `signed_at` | `дд.мм.гггг` |
| Отдел | `department` | код: ЮО, ОБО, НО, HR, ФО |
| Вид услуги | `type` | Разовая услуга, Абонентское обслуживание, Аренда, … |
| Предмет Договора | `subject` | Юридическое сопровождение, Взыскание долга, … |
| Сумма Договора | `amount` | число («1 000 000») или условие словами |
| № Доп. соглашения / дата | `amendments_text` | текст как в книге |
| Предмет доп. соглашения | `amendments_summary_text` | текст |
| Дата расторжения / исполнения | `end_date` | `дд.мм.гггг` |
| Примечания | `note` | текст |
| Дата опл. остатка | `data_opl_ostatka` | `дд.мм.гггг` |
| Текущий статус | `tekuschiy_status` | текст (это не «Текущее состояние»!) |
| Проблемы | `problemy` | текст |
| Источник | `istochnik` | значение списка; новое заведётся само |
| Коммент БИС | `komment_bis` | текст |

**Не присылать** «Оплачено», «Остаток» и «Срок, мес»: KORT считает их сам
(из сводки оплат и выписок). Шлюз вернёт их в `unknown` с пометкой «только
чтение».

Названия колонок можно слать как подписи KORT, как ключи или как заголовки
из исходного Excel/книги - KORT помнит прежние названия колонок, по которым
реестр загружался. Колонку, которую KORT не узнал, шлюз не пишет и называет
в `unknown` каждой строки: сверьте такие вручную.

### Колонки книг BBC, которые легко перепутать

- В книге «BBC Реестр ЮО - Разовые», лист «Разовые»: **«Предмет исполнения»
  - это не «Предмет Договора»** (там «взыскание долга», в реестре -
  «Юридическое сопровождение»). Эту колонку **не отправлять вовсе**: KORT
  помнит заголовок «Предмет исполнения» как прежнее имя «Предмета Договора»
  и принял бы её за него.
- «Статус» в книге «Разовых» → `status`; «Текущий Статус» → `tekuschiy_status`.
- «Факт Дата завершения» → `end_date`; «План Дата завершения» → `planned_end_at`.
- «Ответ Лицо» → `people`.
- В главном листе реестра («ЮО Сводная») последняя колонка без заголовка
  при загрузке ушла в «Примечания»; «*Примечания» - отдельная. Не сливать.

## 3. Шлюз сверки

```
POST /contracts/sync
{
  "source": "Google: BBC Реестр ЮО - Разовые, лист Разовые",
  "rows": [
    {"number": "№ЮО/143", "customer": "Болекпаев Болатжан Калиакпарович",
     "values": {"Текущее состояние": "На исполнении", "Планируемый срок завершения": "28.02.2027",
                "Ответственное лицо": "Нурболат", "Сумма Договора": "400 000"}}
  ],
  "apply": false,
  "overwrite": "empty",
  "create": true
}
```

- `apply: false` (по умолчанию) - **пробный прогон**: только отчёт, в базу
  ничего не пишется. Всегда начинайте с него.
- `apply: true` - записать. Каждая правка идёт тем же путём, что правка в
  карточке: проверка списков и прав, запись в историю договора (там же у
  человека кнопка «Вернуть»), одна общая запись в журнал действий о сверке.
- `overwrite: "empty"` (по умолчанию) - заполнять только пустые поля KORT.
  Поле, где в KORT уже стоит другое значение, **не меняется** - оно в
  отчёте как `conflict`. `overwrite: "all"` меняет и такие - **только по
  явному решению владельца реестра** (см. п. 4).
- `create: true` - заводить договоры, которых в KORT нет.
- Пустое значение в источнике никогда ничего не стирает.
- За один вызов - до 2000 строк.

### Как строка находит договор

По номеру - без «№», пробелов и регистра («№ ЮО/1» = «юо/1»). Если такой
номер у нескольких договоров - ещё по заказчику (без кавычек и регистра).
Не нашлось однозначно - строка **не трогается** (`status: "ambiguous"`,
в `candidates` - id договоров): угадывать нельзя, уточните заказчика.

Сверка видит только договоры, открытые учётке, от которой идёт вызов, - как
реестр. Номер есть, но договор этой учётке не открыт (другой отдел, чужое
юрлицо) - строка не трогается и новый такой же не заводится
(`status: "closed"`). Поле, скрытое от учётки, не читается и не пишется -
оно в `unknown` с пометкой «поле вам не открыто».

### Ответ

```
{
  "dry_run": true,
  "summary": {"rows": 64, "matched": 63, "create": 1, "ambiguous": 0, "errors": 0,
              "same": 900, "fill": 12, "change": 0, "conflict": 40, "applied": 0, "closed": 0},
  "rows": [
    {"row": 0, "number": "№ЮО/41", "status": "matched", "contract_id": "…",
     "fields": [
       {"key": "status", "title": "Текущее состояние", "current": "На исполнении",
        "incoming": "Исполнен", "action": "conflict"},
       {"key": "komment_bis", "title": "Коммент БИС", "current": "",
        "incoming": "через BBC", "action": "fill"}
     ],
     "unknown": ["Оплачено (считается само - только чтение)"]}
  ]
}
```

`action`: `same` - совпадает; `fill` - в KORT пусто, будет заполнено;
`conflict` - в KORT другое, не меняется; `change` - будет заменено (только с
`overwrite: "all"`); `keep` - в источнике пусто, в KORT значение остаётся.
После `apply: true` у строки `applied: true/false` и `error` - почему сервер
не принял (например, «Статус «в работе» нет в списке»).

## 4. Порядок работы и что решает человек

1. Войти своей учёткой.
2. Прочитать книгу Google, собрать строки (номер, заказчик, значения по
   таблице выше).
3. `POST /contracts/sync` с `apply: false` - показать человеку сводку:
   сколько заполнится, сколько заведётся, какие `conflict` и `ambiguous`.
4. `apply: true, overwrite: "empty"` - заполнить пустое и завести новое.
5. **`conflict` не решать самому.** На 29.09.2026 книга «Разовых» и главный
   реестр ЮО расходятся между собой: у 7 договоров в книге «Исполнен», в
   реестре «На исполнении»; у 33 разные плановые сроки; у 12 разные
   ответственные; у 3 разные суммы. В KORT сейчас стоят значения главного
   реестра. Какой источник главнее - решает владелец реестра. Только по его
   слову - повтор с `overwrite: "all"` для того источника.
6. `POST /auth/logout`.

## 5. Пример (Python)

```python
import httpx

BASE = "https://kort.cards/api/backend/api/v1/finance"
with httpx.Client(base_url=BASE, timeout=120) as kort:
    kort.post("/auth/login", json={"email": "…", "password": "…"}).raise_for_status()
    try:
        rows = [{"number": "№ЮО/41", "customer": "ТОО \"ALVIN MARKET\"",
                 "values": {"Коммент БИС": "в 1с висит", "Текущий статус": "в работе"}}]
        plan = kort.post("/contracts/sync", json={"source": "Google: Разовые", "rows": rows}).json()
        print(plan["summary"])
        # показать человеку конфликты; затем:
        # done = kort.post("/contracts/sync", json={"source": "Google: Разовые", "rows": rows, "apply": True}).json()
    finally:
        kort.post("/auth/logout")
```
